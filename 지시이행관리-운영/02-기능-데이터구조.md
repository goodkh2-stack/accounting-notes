# 02. 현재 기능 및 데이터 구조 문서화

## 1. 화면별 기능

### 1.1 대시보드 (`#view-dashboard`)
- 통계 카드 6종: 전체 회의록 수, 전체 지시사항 수, 대기중, 진행중, 완료, 지연(마감 초과)
- **마감 임박/지연 지시사항 표**: 마감일이 오늘 기준 7일 이내이거나 이미 지난(미완료) 지시사항을
  마감일 오름차순으로 표시
- **최근 회의록 표**: 최신 8건, 각 회의록에 연결된 지시사항 건수 표시

### 1.2 회의록 관리 (`#view-meetings`)
- 목록: 일자, 회의명, 구분(경영회의/이사회/부서회의/프로젝트회의/기타), 참석자, 연결된 지시사항 건수
- 검색: 회의명/내용/참석자 텍스트 검색(대소문자 무시)
- CRUD: 새 회의록 등록, 편집, 삭제(연결된 지시사항이 있으면 삭제 전 경고, 지시사항 자체는 유지)
- 회의록에서 바로 "지시사항추가" 버튼으로 해당 회의에 연결된 지시사항 생성 가능

### 1.3 지시사항 이행관리 (`#view-directives`)
- 목록: 제목, 지시자/직급, 담당자/부서, 우선순위, 마감일, 상태
- 필터: 상태(대기/진행중/완료/보류/지연), 우선순위(긴급/높음/보통/낮음), 지시자(등록된 지시자 목록에서 자동 생성)
- 검색: 제목/내용/담당자 텍스트 검색
- CRUD: 새 지시사항 등록, 편집, 삭제
- **이행 이력 자동 기록**: 저장 시 상태가 바뀌었거나 경과 메모를 입력하면 `history` 배열에
  `{날짜, 상태, 메모}` 항목이 자동 추가됨(추가만 가능, 수정/삭제 불가 — 감사 추적 목적)
- **지연 판정**: `status !== '완료'`이고 `dueDate`가 오늘보다 이전이면 목록/대시보드에 "지연"으로 표시
  (저장된 `status` 값 자체를 바꾸지는 않고, 화면에 보여줄 때만 `effectiveStatus()`로 계산)

### 1.4 데이터 백업 (헤더 버튼)
- **내보내기**: `meetings`, `directives` 전체를 JSON 파일로 다운로드 (`directive-tracker-backup-YYYY-MM-DD.json`)
- **가져오기**: JSON 파일을 업로드하면 현재 데이터를 통째로 교체(확인 창 노출 후 진행)

## 2. 데이터 구조 (스키마)

### 2.1 저장 위치
브라우저 `localStorage`에 아래 두 키로 JSON 문자열로 저장됩니다.

| localStorage 키 | 내용 |
|---|---|
| `meetings_v1` | 회의록 배열 |
| `directives_v1` | 지시사항 배열 |

### 2.2 회의록(Meeting) 스키마
```ts
{
  id: string;          // "id-<timestamp36>-<random6>" 형태의 고유 ID
  date: string;         // "YYYY-MM-DD"
  type: string;          // "경영회의" | "이사회" | "부서회의" | "프로젝트회의" | "기타"
  title: string;         // 회의명 (필수)
  attendees: string;     // 참석자, 쉼표 구분 자유 텍스트
  content: string;       // 회의 내용/안건 자유 텍스트
}
```

### 2.3 지시사항(Directive) 스키마
```ts
{
  id: string;
  title: string;              // 지시사항 제목 (필수)
  description: string;        // 상세 내용
  instructorName: string;     // 지시자 이름
  instructorRole: string;     // "대표이사(CEO)" | "CFO" | "COO" | "CTO" | "CMO" | "이사회" | "기타 임원"
  assignee: string;           // 담당자
  dept: string;                // 담당 부서
  priority: string;            // "긴급" | "높음" | "보통" | "낮음"
  dueDate: string;              // "YYYY-MM-DD" (선택)
  status: string;                // "대기" | "진행중" | "완료" | "보류" | "지연"
  meetingId: string | null;      // 연결된 회의록 id (없으면 null)
  createdAt: string;              // ISO 8601 타임스탬프 (등록 시점, 수정되지 않음)
  history: Array<{
    date: string;                 // 사람이 읽는 로케일 문자열 (toLocaleString('ko-KR'))
    status: string;               // 그 시점의 상태
    note: string;                 // 경과 메모 (없으면 기본 문구 "상태 변경"/"지시사항 등록")
  }>;
}
```

### 2.4 관계
- `Directive.meetingId` → `Meeting.id` (다대일, 선택적) — 회의록 하나에 여러 지시사항이 연결될 수 있음
- 회의록 삭제 시 연결된 지시사항은 삭제되지 않고 `meetingId`가 가리키던 값이 남음(참조가 끊긴 상태로 유지됨;
  현재 코드는 이 경우 별도 정리(cascade)를 하지 않음)

## 3. 알려진 한계

- 서버/DB가 없어 **여러 사용자 간 데이터 공유 불가** — 각 브라우저 프로필에 독립적으로 저장됨
- localStorage는 브라우저 데이터 삭제 시 함께 사라짐 → 정기적인 "내보내기" 백업 필수
- 입력값 유효성 검사가 최소 수준(제목 필수 체크만 존재), 날짜/이메일 형식 등 세부 검증 없음
- 동시 편집 충돌 처리 없음(단일 사용자 로컬 저장 전제)
